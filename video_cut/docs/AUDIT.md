## 1. 剪辑中间产物能否暂存？ —— ✅ 可以，且默认安全

**现状结论：**
- 每次渲染分两段：各轨先渲成**无损中间文件**（matroska，ffv1 视频 + pcm 音频），再合成最终片。
- 默认：中间件放在临时目录，渲染结束**自动删除**（不污染磁盘）。
- 需要暂存时：导出对话框勾选 **「保留中间产物」** → 中间件存到 输出名_中间产物/ 文件夹（含字体、文本文件），供调试/复用/二次处理。
- 引擎 API：`render(..., intermediates_dir=路径)` 可直接指定目录（测试中验证过）。

**已知限制（诚实说明）：**
- 目前**没有增量缓存**：改了时间轴任意片段，下次渲染会全部重渲（不做"哪轨没变就复用"的智能判断）。
  这是将来的优化项（轨道粒度缓存：按 轨道ID+片段哈希 判失效）。
- 中间件是 ffv1 无损，体积约为源素材的 1.5~3 倍，属正常。

## 2. 剪辑素材能否不被破坏？ —— ✅ 保证不被修改（有测试断言）

**现状结论：**
- 应用对源素材**只读**：扫描/ffprobe/解码均不写源文件；片段只记录源路径。
- 所有写操作只发生在：临时目录（中间件）、thumbs_cache（缩略图）、logs（日志）、项目目录（.vcp/自动保存）。
- **自动化保证**：test_engine.py 在渲染前后对全部源文件做 mtime+size 快照比对（断言"渲染修改了源素材文件！"会失败），已通过。
- 程序内不提供"删除/改名/覆盖源文件"的任何入口；纹理包（滤镜/文字的字体）只复制不进源目录。

**已知限制：**
- 项目文件存的是**绝对路径**：素材被移动/改名后项目会找不到文件（打开时会报错提示）。将来可做"相对路径/重链提示"。
- 若用户在外部程序里修改素材文件本身，与本应用无关，但缓存（缩略图/波形）会因哈希失效自动重建。

## 3. 是否有自动命名的能力？ —— ✅ 有（多级自动命名）

| 场景 | 命名规则 | 示例 |
|------|---------|------|
| 导出成片 | 项目名 + 分辨率 + 时间戳（可手改路径） | `我的项目_1920x1080_20261003-1130.mp4` |
| 中间件 | track_0.mkv / track_1.mkv…（在指定中间目录内） | |
| 缩略图/波形缓存 | 路径+大小+mtime 的 MD5 哈希，自动去重 | `a1b2….png` |
| 日志 | app.log → 1MB 滚动 app.log.1/.2/.3 | |
| 自动保存 | autosave.vcp（启动可恢复） | |

时间戳命名天然避免重名覆盖；用户也可以自由改路径后缀自动切换（mp4/mov/webm）。

## 4. 终极视频是否有画质降低的可能？ —— 有，但透明可控

**画质链路分析（从源到成片）：**

```
源素材 ──trim/变速/缩放（采样重定位，无有损编码）──▶ 无损中间件(ffv1+pcm) ◀──▶ 最终编码(h264/AV1)
        ↑ 这一步零损失                          ↑ 无损，可反复复用          ↑ 唯一有损环节
```

- **唯一有损的环节 = 最终编码**，画质由用户选择的 CRF 决定：
  - 高 16 / 中 20 / 低 26 / 更低 30 / **无损(CRF 0，文件巨大)**
- 中间件 ffv1 是无损编码（像素级保真）+ pcm 无损音频 → **不产生"一代比一代糊"的生成损耗**；
  调色/重渲多次也不会累积劣化（这是与"直接输出就完事"的剪映式流程的最大差异点之一）。
- 已知的固有损耗（与任何剪辑软件相同，如实说明）：
  - **升分辨率不增加细节**：720p 素材导出 1080p 只是拉伸，不会更清晰；
    建议导出分辨率 ≤ 素材实际分辨率。
  - 预览播放走 rgb24 转换（仅预览，不影响成片）。
  - overlay 叠加需要 RGBA 中间转换，属无损（ffv1），无视觉损失。
- 建议：日常用「中」即可；想给第三方二次剪辑建议 **保留中间产物**（无损原件）。
